The v2 System

How the v2 system runs end to end: the Tuesday-close decision, your orders sized for the real book, the V2_System watchlist in TradingView, what S4, S5 and the reviewer do with it, pyramiding onto current-system holdings, the auto-trail and its static-IP relay, the v2 page, and the files that carry each step.

The design and the evidence are in Doc 41; the rules and their tests in PREREG_v2_house_rules and PREREG_v2_borrowed_rules. This document is how v2 RUNS, end to end — every step, who does it, when, and which file carries it to the next step. It is defined first; the components are built to it.

1. Scope and decisions it rests on

  • v2 runs in full form now, for real money, beside the current system (Jay, 18 Oct). It does not wait for 16 Jan 2027 — but it only BUYS when the Nifty 500 is above its 200-day SMA, so in practice real buying starts when the market recovers. The paper books keep running as the record.
  • Capital: one-third of the trading capital (house sizing capital ÷ 3 = ₹10,00,000 today; V2_CAPITAL in .env overrides). The current system keeps the rest.
  • The live rule set is V2H (v2_house.V2H_LIVE): P1E's ensemble rank, top 25 %, 0.10 % of equity per ATR20, Wednesday rebalance, a 4 × ATR14 disaster stop with the house Chandelier trail, tax-aware runners + monthly risk trims, the ETF sleeve (own pool, NAV premium ≤ 3 %), sector cap 25 %, correlation block 0.90, per-trade cap 3.33 % of equity; earnings and stale-data guards.
  • No targets, no intraday triggers. The trigger is the weekly rank at Tuesday's close.

3. The TradingView list and what S4 / S5 do with it

  • Name: V2_System-DDMONYY (the date of the run). Names in this order (the Add-ons line on the chart says which group a name is in): BUY (this week's buys — yours and the V2H paper book's), SELL, HOLD (your v2 holdings, then paper), WATCH (the top 30 of the rank, for context).
  • S4 and S5 are execution aids for v2, not judges. The reviewer reads them on the Daily chart for each buy and is told the selection is already made: it looks only for reasons not to buy at Wednesday's open — over-extension, results within the week, a wall within 1 ATR, a gap, thin liquidity. A WAIT or PASS means skip that buy this week; the name comes back next Tuesday if it still ranks.
  • Ignore S4's own VERDICT / GO / TAKE-IT rows on v2 names — those are the current system's entry rules (PA, location, volume, bar), which v2 deliberately does not use.
  • Add-ons M2 (v2 status) prints the v2 facts on the chart of any v2 name: rank of N, the section (BUY / SELL / HOLD / WATCH), the disaster or trailed stop (drawn as a line), real or paper holding, and the date of the decision. Pushed nightly with the status file; display only.

6. Data contracts

  • Journal: a v2 holding is an OPEN row with setup = POS-V2, Timeframe = Positional, initial_sl = stoploss = disaster stop, no targets. This is how v2 tells its holdings from the current system's.
  • FINAL_V2_WATCHLIST.csv: Symbol, Section, Rank, Stop, Held.
  • data/v2/addon_status.txt: one line, _ASOF:<date>;<fill date>,SYM:<rank>/<n>;<section>;<stop>;<held>,… (each -/& symbol also under TradingView's _ spelling).
  • Order sheet: the paper books, then ## YOUR v2 ORDERS with side, shares, value and stop.

7. Risk controls and the open decisions (Jay)

In force: the regime gate, the resting disaster stop + Chandelier trail, per-trade cap 3.33 %, sector cap 25 %, correlation block, ETF NAV premium and liquidity floors, earnings and stale-data guards, the reviewer's one-week deferral.

Open:

  1. The house open-risk budget and the 25-position limit. Both starved v2 in the test. Proposal: they apply to the current system's book; v2 is limited by its own capital slice and rules.
  2. A name held by both systems. Proposal: v2 does not buy a name the current system already holds (no double exposure); it still holds what it owns.
  3. Order type at Wednesday's open. Proposal: a limit at Tuesday's close + 1 %, cancelled if unfilled by 10:00 (the backtest filled at the open price).
  4. Automatic trailing at Dhan needs a static IP registered with Dhan (deferred) — until then the trail is raised by hand from Risk Shield.

8. Decisions of 18 Oct (evening) and the designs they need

D1 — house limits. The open-risk budget, exposure tiers, circuit breaker, 25-position limit and the order gate count only the current system's positions (built).

D2 — v2 may pyramid onto a current-system holding (Jay: with positional trades auto-trailed, both systems exit the same way). Design, keeping the house invariant of ONE journal row and ONE stop price per holding:

  • The v2 ledger data/v2/real_book.json is v2's record of ITS shares: per symbol, shares, entry, entry date, the add's disaster stop. The journal keeps one row per symbol (owned by whichever system bought first); journal_sync keeps that row's quantity equal to Dhan's total.
  • v2 buys a name the current system holds → the order sheet marks it PYRAMID (onto a current-system holding); after the fill there is still ONE resting stop for ALL shares, at the higher of the holding's current stop and the add's disaster stop (fill − 4 × ATR14). v2_take.py records the slice in the ledger and leaves the journal row alone.
  • v2 sells its slice when the rank says so: the order sheet gives the slice's shares only; v2_take.py SYM --sell --price P closes the slice; the current system's shares stay.
  • A stop fill sells everything (one stop): the nightly run sees the journal row CLOSED and closes the slice too, at the journal's exit price.
  • v2's limits (per-trade cap, sector cap) count v2's slices; the current system's count its rows.

D3 — Wednesday order type: a limit at Tuesday's close + 1 %, cancelled if unfilled by 10:00.

D4 — auto-trailing, for v2 holdings AND the current system's POSITIONAL holdings; swing trades are NOT trailed (Jay). Design (gtt_auto_shield --trail, one pass per Dhan stop order):

  • level = the house positional Chandelier (highest close since entry, 22 sessions, − 4.5 × ATR22);
  • never closer than 3 × ATR14 to the last close (house_policy.DHAN_STOP_MIN_ATR): the new stop is the LOWER of the two, so a trail can never sit inside normal daily noise;
  • raise-only; once a day after the close (15:45), on closing prices; never sells — if the level is at/above the close it is reported as an exit review, not placed;
  • a hand-set stop (Risk Shield override) is the floor (Floor mode) or the stop itself (Exact mode);
  • dry run first: each evening a Telegram lists the moves it would make; nothing changes at Dhan until Jay switches it live — which also needs the static IP registered with Dhan (DH-905).

D5 — a full v2 page in Web Commander (EXECUTION › 🧭 v2 SYSTEM), separate from the paper page: status strip (regime, next decision and fill dates, v2 capital, equity, cash); this week's orders for your book with the reviewer's rulings and the pyramid list; your v2 book (slices, stops, Chandelier, rank now); the rank board with filters and the ETF pool (premium, liquidity); risk (sector weights vs the 25 % cap, per-name size vs the cap); the trail proposals; the weekly checklist; rules and evidence. The paper books stay on 🧭 PAPER · v2 SYSTEM.

9. The static-IP relay for Dhan order calls (JioFiber has no static IP)

Dhan accepts order placement and changes only from the IP registered on the account (DH-905 otherwise); data, holdings and the journal sync are unaffected. Jio gives no static IP at home, so a small AWS Lightsail server in Mumbai with a static IP relays ONLY the order calls. It is reachable only over Tailscale — the proxy is never open to the internet — and the Dhan token is never stored on it.

Jay's part (account and payment are yours):

  1. Create an AWS account; open Lightsail → Create instance → Region Mumbai (ap-south-1), Linux, Ubuntu 24.04, the cheapest plan with a public IPv4 (the $3.50 plans are IPv6-only).
  2. Networking → Create static IP → attach it to the instance. In the instance's firewall, keep only SSH (22).
  3. Open the instance's browser SSH and paste: `` curl -fsSL https://tailscale.com/install.sh | sh sudo tailscale up --hostname=dhanrelay sudo apt-get update && sudo apt-get install -y tinyproxy sudo sed -i 's/^#\?Port ./Port 8888/; s/^Allow ./Allow 100.64.0.0\/10/' /etc/tinyproxy/tinyproxy.conf sudo systemctl restart tinyproxy echo 'precedence ::ffff:0:0/96 100' | sudo tee -a /etc/gai.conf && sudo systemctl restart tinyproxy ` The last line makes the relay prefer IPv4: Dhan's API is on CloudFront, which also answers over IPv6, and a Lightsail server is dual-stack - without it Dhan sees the server's IPv6 address and replies DH-905 although the IPv4 is registered (found 18-Oct). (sign the tailscale up` link in with the same account as the PC).
  4. On the PC, add to .env: DHAN_ORDER_PROXY=http://dhanrelay:8888, then run python dhan_relay.py --check — it prints the relay's public IP. It must equal the Lightsail static IP.
  5. Register that IP at web.dhan.co → Profile → Trading & Data APIs → static IP. It locks for 7 days, so do step 4 first.
  6. Refresh the Dhan access token after registering the IP (python dhan_auth.py --force): Dhan applies a newly registered IP only to tokens issued after it — the 18-Oct test was refused (DH-905) with the earlier token and accepted right after a refresh. The 08:00 job refreshes daily anyway.
  7. python dhan_relay.py --test-modify re-submits one OCO and one SINGLE stop at their SAME values through the relay (it asks first). "RELAY WORKS" → remove --dry-run from run_gtt_trail.bat. Passed 18 Oct 2026 (both kinds accepted via 16.4.135.197; read back unchanged).

The code side (built): dhan_relay.py wraps the dhanhq order methods once per process (installed by dhan_auth, and by n8n_order_handler); with DHAN_ORDER_PROXY unset nothing changes. Every surface that places or changes an order — the trail, Risk Shield's tighten buttons, the webhook, the MCP server — goes through the relay the moment the variable is set.
