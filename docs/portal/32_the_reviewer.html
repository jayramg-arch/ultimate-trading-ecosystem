Doc 32 · The live system

The Reviewer

A second pair of eyes on the panel, not a second panel. S4 rules by template; the reviewer reads every cell of S4, S5 and the index chart, weighs them against the desk's own doctrine, and writes a case for, a case against, a ruling and a plan — then the script checks the arithmetic it is not trusted with. It runs in the evening over the board, on demand for one name, and by itself the moment an S4 GO alert fires.

The three ways in

evening  → --board 75m --live
one name → SYMBOL --tf 75
alert    → webhook → Telegram
All three write the same file, the same log row, and the same page — The Reviewer Log, Doc 31.

01The job

S4's VERDICT and SUMMARY are a fixed template. They restate rows; they cannot weigh one against another — RV 0.72 on a pullback into a monthly zone is not the failure that RV 0.72 on a breakout is, and the template cannot say so. The reviewer (s4_review.py, 11 September) is the deliberation layer the panel does not have. It receives the complete contents of every panel on the chart, the drawn levels, the last sixty bars and whether the name is already held, and is told to read every field itself and to treat S4's ruling as one opinion among the inputs, considered last.

S4's verdictThe reviewer
NatureTemplate — the first matching rule winsDeliberation — case for, case against, a named deciding factor
SeesIts own rowsS4, S5, the v67 dashboard, Unified, the Zigzag, the drawn levels, the bars, the journal, and for an ETF the index chart
WeighsCannotContext over trigger; location as the gate that expires; volume by setup type; room as information; participation as one story
ArithmeticExactNot trusted — the script recomputes R from the plan and appends the canon
AuthorityThe plan of recordAdvice, logged for scoring. Your chart-read has veto
The rule that makes it safe to use

It may talk you out of a trade the panel armed. It never talks you into one the panel did not. A name reaches the reviewer only as a GO row, a Buy Trigger Live row, an alert, or your explicit command — it does not go looking. And every PASS must name the one change that would make it a TAKE, or it is a WAIT.

02What it reads — its own chart tabs

The read is over the Chrome DevTools Protocol against TradingView Desktop (launched with --remote-debugging-port=9222, i.e. LAUNCH_TRADINGVIEW_CDP.bat). It walks every open chart tab, pulls each study's table cells, labels, lines and boxes through TradingView's own drawing collections, and merges them. Cells arrive unordered and are re-sorted by row; the accessors fail loudly (“panel path not found”) rather than returning an empty panel, because a desktop update can rename the internals.

TabCarriesWhat the reviewer takes from it
S4 stackS4 · Swing Pro v67 · Unified · ZigzagThe five-gate TRIGGER row, location, room, OI and options rows, the plan, the verdict and SUMMARY; v67's FUTURES OI STATE and context; the Zigzag's structure
S5Section Five aloneParticipation (footprint delta, divergence, value area) and the Setups band in full. Geometry, Levels and the Read are withheld — replaced by “[withheld: not yet fine-tuned]” before the model sees them (S5_SKIP_SECTIONS)
S4 Reviewer · S5 ReviewerCopies of the two stacks above, for the reviewer's exclusive useSince 21 Sep. Named in S4_REVIEW_CHARTS (two chart ids); when set, these are the only tabs the reviewer switches and reads, so your own S4 and S5 tabs never move. Before this, every review took your chart for ~90 s — 31 reviews on 18 Sep was 49 minutes. If the two tabs are not open the review fails loudly rather than falling back to yours
Phase-1The S4 stack again, for the underlying indexOnly for an ETF. Designated by S4_PHASE1_CHART in .env; the ETF → index map is data/tv_index_map.json. Read first, labelled PHASE-1, and the ETF's own chart becomes PHASE-2

On top of the panels: the last 60 bars of the chart TF (--bars), and a position context line — HELD qty / price / stop / target / timeframe / setup / days from the journal, and the PYRAMID class, R and add-stop from FINAL_Portfolio_Picks.csv — so an add on a held name is judged as an add. Since 22 September it ends with the earnings distance — earnings in 37d (2026-10-29) — because a binary event inside the hold is the one thing a price panel cannot see, and it changes size, not direction. A name whose date is unknown prints nothing: "no earnings" would read as safe, and roughly half the book has no date at all.

The two tabs must agree

The merge refuses if the S4 and S5 tabs disagree on symbol or timeframe. Switching is done for you — the script sets the symbol and TF on every tab and waits for the studies to finish loading before it reads — but a tab that is a duplicate of the same layout shares its id with the original and cannot be driven separately. The Phase-1 and Reviewer tabs must each be a copy of the layout (“Make a copy”), not a second view of it. A layout's id is stable — it is the saved layout's, not the tab's — so closing and reopening the same named layout keeps the ids in .env valid.

Settling, and the retry

After a switch the reviewer waits for every study on both tabs to finish recalculating before it reads. That window was 45 s; on 21 Sep three of three reviews that arrived first in a batch — and every batch starts at a bar close, when TradingView is recalculating everything — timed out, while the five that ran a minute later all passed. It is now 90 s (S4_SETTLE_S), with one retry after 20 s on a settle timeout. A review that still fails writes no .md, so it has no row in the Log — only the Telegram FAILED message.

The banner

Reviewer Banner on the taskbar is a small always-on-top strip fed by logs/reviewer_status.json, which the receiver writes at each transition: red while a review runs (name, TF, seconds, how many are queued), amber while the reviewer's tabs are put back, green idle with the last name and its time. Drag it anywhere; right-click closes it. It reads nothing else and can be started or stopped at any time.

03The doctrine it applies

The system prompt is the desk's rulebook, measured on its own trades, and it is the only thing that makes this more than a language model reading a table. The parts that decide rulings:

RuleWhat it says
Context outranks triggerStage 2 with a rising 30-WMA, RS leadership, RRG LEADING / IMPROVING, sector not Stage 4 — these decide whether a trigger is worth taking at all. A Stage 3/4 name is NO TRADE regardless of the trigger.
Location is the gate that expiresFresh, controlling, Monthly / Weekly zones containing price, S/R with few tests — strong. Tested zones, MTTWR levels, AVWAP / EMA-only location — weak. A “weak location” GO is a momentum chase
Volume by setup typeA breakout needs RV ≥ 1.0; a pullback into a zone does not — median RV on at-value bars is 0.63 and low RV there is not predictive of failure. It must not fail a pullback for breakout volume
Room is informationMeasured 11 Sep on 331 GO-timed trades: 77% had under 1R to the first obstacle and did not do worse; blue sky was the worst bucket. The first obstacle is the trade's first test, graded TOLERABLE on its own. It becomes FATAL only with other evidence of supply — bleeding delta, a rejection wick, a heavy call wall, Stage 3 context. “No room” may never be the deciding factor
T1 follows the canonSwing 2R / 4R, positional 3R / 5R, nothing under 2R. When S4's plan prints a T1 sitting on the obstacle below 2R (tagged ·lvl), the reviewer must say so and replace it with the canon T1 in its plan
Extension> 2.5 ATR above the daily EMA20 is a warning; > 4 is a veto for a fresh entry — wait for the pullback the panel names
Participation, activelyFutures OI four states (long build-up strongest; short covering fades; short build-up is fuel if a trigger fires on volume); options by field when the row has numbers — PCR, max pain and its pull, ATM ΔOI, the writer strikes as obstacles above and shelf below; AVWAP as location only in confluence; VP value area; footprint delta to break ties. Read as one story
Two OI rowsS4 pairs the daily OI change with the last chart-TF bar; v67 pairs it with the daily futures close. When they differ it must say so and take v67's state for the day's positioning
ETFs — two phasesPhase-1 is the index: its stage, location, trigger and room are the thesis. Phase-2 is the ETF: tradability, fills, thin volume. INDEX ARM = ETF WAIT (house rule, 13 Sep): if the index's own TRIGGER row is not GO, the ETF cannot be TAKE. Index in Stage 3/4 = NO TRADE

Tone rules

Case FOR first, honestly weighted, then case AGAINST with each risk marked FATAL or TOLERABLE. A GO with clean context and location is a TAKE — “risks remain” is never a reason to pass. Say what a good version of this setup looks like and how close this one is. Where S4's own rows contradict each other, say which it believes and why. Only reason from what is in the read: “S4 not on chart” is a legitimate answer, and a field showing “-” is unknown, not neutral and not a fail.

The model

Default gemini-3.1-flash-lite — the tier the rest of the app uses. --provider claude is opt-in (S4_REVIEW_ANTHROPIC_KEY, claude-opus-5). Flash-lite is fast and cheap and its judgement has been worth having; its arithmetic and its habit of writing “v67 confirms this” against a row that said the opposite are exactly why section 08 exists.

04The evening pass — over the board

python s4_review.py --board 75m --live
python s4_review.py --board 125m --live

Reads gm_board_cache_75m.csv (or 125m, daily), selects every row whose S4-GO column matches N/N GO — 5/5 GO today, 4/4 GO on older caches — and with --live adds every row whose Category starts Buy Trigger Live, bull and recovery. That second set is how the recovery names get read: a recovery trigger is typically 3/5 · no vol, the normal shape for that path, and would never appear on a GO-only pass.

It prints the list and the cache's age, and warns ⚠ STALE — rebuild it past six hours. Take the warning: past it you are reading last session's rows against today's chart. Since 16 September the auto-pilot's Phase 12 rebuilds all three boards at 16:30, so the cache is fresh by the time you sit down.

Each name takes about a minute; an ETF about ninety seconds, because the index is read first. The names run in sequence — the charts are switched, read, and the review written before the next one starts — so a twelve-row board is a quarter of an hour. Start it, do something else, come back to the Log.

05Alert-triggered — the reviewer runs itself

Since 16 September an S4 GO alert reviews its own name. The chain, and the one thing you do each morning to keep it alive:

1

Before the open — one click

S4 Alert Reviewer on the taskbar (START_ALERT_REVIEWER.bat). It starts the webhook receiver on :8000 and the ngrok tunnel on your static domain (NGROK_DOMAIN in .env). Two console windows stay open; closing them stops it. The receiver restarts itself if it ever exits; ngrok is not started twice.

2

The alert fires on TradingView's servers

The S4 GO alert's Notifications tab carries the Webhook URL — https://<NGROK_DOMAIN>/s4-review?key=<S4_REVIEW_KEY> — and S4's default message, which begins {{ticker}} S4 GO {{interval}} - …. That prefix is all the receiver needs; a JSON body {"ticker", "interval"} is accepted too.

3

The receiver checks the key and queues the name

/s4-review in dhan_tv_webhook.py. Fail-closed: no key configured, or a key that does not match, is rejected. The same symbol + TF inside 30 minutes is a duplicate and skipped (S4_ALERT_DEDUP_MIN); a 75m and a 125m alert on one name are two reviews, by design — different bars.

4

One worker, in order

A review takes both chart tabs over for 60–90 seconds. Five alerts at a 75m close would fight for the charts; queued behind a single worker they arrive over ~5 minutes, which is fine — the alert marks a bar, and the bar does not change. The chart is switched back to whatever it showed before (S4_ALERT_RESTORE_CHART=0 to leave it).

5

Telegram, ~90 s after the ping

The Telegram-sized cut: RULING · WHY · PLAN · FLIPS IF · R-CHECK · OI-CHECK, and the path to the full file. The review is saved and logged exactly as an evening one, and the Reviewer Log page is rebuilt.

If the reviewer is down, the alert is lost — not retried

TradingView posts once. With the receiver down it gets a 502 and moves on; the phone push still arrives, only the review is lost. That is why the launcher restarts the receiver and why “the alert reviewer is up before the open” is on Doc 26's list of things that fail silently. Check logs/s4_alert_review.log for queued … reviewed in Ns (telegram sent).

Read a name on demand — REVIEW.bat

Since 21 Sep. REVIEW TITAN 75 (or run it and answer the two prompts) posts to the local receiver, so a manual read takes exactly the alert’s path: the queue, the 30-minute dedup, the reviewer’s own tabs — never yours — the banner, Telegram and a row in the Log. Use it when the board or your own S4 read wants the full case on a name that has not pinged, or to re-read one after the bar. “duplicate within 30 min” means it was read recently.

Test it without an alert

curl -X POST "https://<NGROK_DOMAIN>/s4-review?key=<KEY>" --data "RELIANCE S4 GO 75 - test"

A queued reply, a review on Telegram ninety seconds later, and the chart back where it was. A rejected reply is the key; a hang or a 502 is the receiver.

The alerts themselves

Two per evening on the new dated watchlist — 75m and 125m — each with the webhook URL in Notifications. Clone keeps the URL. Recreate rather than edit: yesterday's alert points at a watchlist that no longer exists and fails to save, and every S4 recompile deletes all alerts regardless. The full ritual is in Doc 26.

06One name, on demand

python s4_review.py                          # whatever the charts show now
python s4_review.py TITAN --tf 75            # switch symbol / TF first, wait, read
python s4_review.py --symbols A,B,C --tf 125
python s4_review.py TITAN --telegram         # also post it
python s4_review.py TITAN --dump             # the raw panel read, no model call

--dump is the diagnostic: it prints exactly what the model would have been given. When a ruling looks wrong, read the dump before blaming the model — most bad rulings are a row that read blank because a bundle was not pasted, a source unbound after a compile, or S5 on the wrong tab.

07The review — three parts, fixed headings

PartSectionsRead it for
ANALYSIS1 Context & trend stack · 2 Location · 3 Room & obstacles · 4 Trigger & gates · 5 Participation · 6 Structure (S5) · 7 The panel's own plan · 8 ContradictionsA trader walking a colleague through the chart — each section quotes the panel's numbers and says what they mean. Section 8 is where S4-vs-v67-vs-S5 disagreements are named and settled
DELIBERATIONCase FOR · Case AGAINST (each line FATAL or TOLERABLE) · Where S4 is too bluntThe weighing. “Where S4 is too blunt” is the part the template cannot write: what a good version of this setup looks like and how close this one is
RECOMMENDATIONRULING · DECIDING FACTOR · LEVEL VALIDATION · PLAN · FLIPS IFThe plan states the trade type first, then entry method, stop, T1/T2 with R — on the canon for that type. FLIPS IF is what would change its mind

The rulings

TAKE   TAKE · reduced size   WAIT for <bar / level / event>   PASS   NO TRADE (stage)

A WAIT names the specific thing it is waiting for. A PASS names the one change that would make it a TAKE — if it cannot, the rule says it is a WAIT. NO TRADE is stage, and only stage. These are the same five pills on the Reviewer Log, so a day's tally reads at a glance.

08The script's checks — appended, never edited in

Five deterministic pre- and post-reads run around the model. They are computed by the script, not the model, and the model's text is never edited — the check is appended below it, so the Log shows both what it said and what the arithmetic says.

CheckWhat it doesWhy it exists
R-CHECKRe-parses the PLAN's entry and stop, recomputes every R the model labelled, and prints the canon line — canon positional 3R/5R: T1 … · T2 … — flagging a T1 under the floor and a TAKE whose reward bar is not met on its own numbersFlash-lite wrote “T1 13.28 (1.5R)” on entry 13.07 / stop 12.60 — 0.45R. Take the R numbers from the canon line, never from the prose. s4_take.py reads the same line
OI-CHECK · OPTIONSReads S4's Futures OI row and v67's FUTURES OI STATE before the model sees them; on a conflict, injects a non-negotiable pre-read (report both, take v67's) and prints OI-CHECK: … CONFLICT. Lists every options field present and requires each to be named in section 5 and the call wall / max pain above price in section 3The model wrote “v67 confirms this” against a row that said the opposite, and skipped options fields it found inconvenient. A flat day still produces a conflict (cash −0.1% vs futures up) — that is the two windows, not a bug
LEVEL CHECKSince 21 Sep. Answers the plan's four levels against the derivatives and the flow: T1 beyond the call wall (and the R actually reachable to it), the stop above the put wall, max pain or the futures long basis sitting inside the entry→T1 path, PCR, OI state, and the footprint delta on the read bar. Goes into the prompt before the deliberation using the panel's levels, and is printed after it against the levels the model actually wroteThe panel printed the walls for months and nothing ever capped a target because of them — a plan could promise 3.0R straight through a strike option writers defend. They grade; they never gate
LV-AUDITVerifies that the model's LEVEL VALIDATION block exists and that each of the four levels carries a number. Shape only — it cannot judge the reasoningA required section is worth nothing if its absence goes unnoticed. Same idea as R-CHECK catching a mis-stated R
INDEX-CHECKFor an ETF, reads the PHASE-1 block's TRIGGER row. Index NO TRADE by stage → ETF NO TRADE. Index not GO → the ruling cannot be TAKE; if the model ruled TAKE anyway, the script overrules it to WAIT and says so on the ruling lineINDEX ARM = ETF WAIT is a house rule (13 Sep). A rule the model is asked to follow is a suggestion; a rule the script enforces is a rule

08bThe derivatives layer — what it is for

Jay, 21 September: "we have not been leveraging the Futures OI, Options OI and Footprint data to effectively validate the Entry, SL, T1 and T2 levels. This is one of the major reasons why I'm losing trades." The data was already on the panel. What was missing was a history to validate it against, and any rule that let it touch a level.

The four levels, each answered

LevelWhat the derivatives say about it
T1Beyond the call wall? Then the reachable R is the R to the wall, not to the target — and under the 2R canon floor that is a half-size or a skip, not the R the plan claims
STOPAbove the put wall? A wash into the floor writers defend takes you out before the level that is actually held. Widening it means resizing, not just moving it
The pathMax pain between entry and T1 pins against the target; the futures long basis inside the path is trapped longs who sell there to get out flat; PCR under 0.7 is a call-heavy book that caps rallies
ENTRYFootprint delta against the trade, or a bearish delta divergence, means flow does not confirm — size down, or wait for a bar where it does
T2Context only. Near-month positioning says nothing about a level the walls will have rolled past. T2 rests on structure
A ceiling is not a target

The correction the first live run forced. Given the facts, the model parked T1 on max pain (0.35R) and T2 on the call wall (1.12R) — it had absorbed "there is a ceiling" and lost "so this is not a trade here". Max pain is an expiry magnet and a wall is where writers defend: you scale before them, never target them. If that is all the room there is, the trade is not available at that entry — wait for a lower one, or pass. A 0.4R plan is a losing trade written down politely. The rule is in the prompt and enforced in the check, so it does not depend on the model remembering.

Six months of history, so this can be measured rather than believed

NSE publishes a daily F&O bhavcopy carrying every contract — 629 stock futures and 29,824 stock options on a single day — and the archive goes back years. fno_bhavcopy.py reconstructs from it exactly what the panel prints: near-month futures OI and change, PCR, max pain, both walls, ATM ΔOI. Checked against the live chain on the same day, the reconstruction is identical. Backfilled 27 March → 21 September: 25,210 rows, 219 names, and a Task Scheduler job appends each evening at 18:45. Every review also records its own derivative and flow fields as columns.

Why that matters more than the rules themselves: six additions to this system have been tested and rejected, one of them backwards. These grade and inform; none of them gates. Whether a wall-capped T1 actually pays better than the canon T1 is a question for the measurement, and the history to answer it now exists.

09The Reviewer Log — Doc 31

Every review is a file, logs/ai_reviews/<ts>_<SYMBOL>_<tf>.md — the review, then the complete panel read under it — and one row in logs/ai_review_log.csv: timestamp, symbol, TF, S4's verdict, the ruling line, the provider, the file, and two empty columns, my_call and agreed, that are yours. build_review_portal.py renders all of it to one page, rebuilt after every alert review, at the end of Phase 12, after s4_take, and by hand any time.

On the pageMeaning
Days, newest firstToday open, older days collapsed. Each day's header carries a tally of its rulings as pills
One row per reviewTime · symbol · TF · the ruling pill · S4's own verdict beside it, so template and deliberation can be compared at a glance
Folded bodyThe full review; the panel read folded again beneath it — there for the “why did it say that” moment, never in the way
TAKEN / SKIPPEDThe block s4_take.py appends, rendered as its own band with your call. This is the scoring
FilterOne box: symbol, ruling, TF, date. Days with nothing matching hide
Header countsReviews · scored · agreed. The last two are empty until you mark trades — and they are the only way the Log can ever say whether the model deserves the trust
Retention — nothing is deleted

These are the forward record: the ruling before the outcome was known. Age is handled by presentation (collapsed days, the filter), not by pruning. A review you disagreed with is worth more to the score than one you agreed with.

10Marking a trade — s4_take.py

python s4_take.py CHOLAFIN                                   # latest review; plan entry, panel qty
python s4_take.py CHOLAFIN --tf 125 --price 1768.5 --qty 20   # the actual fill
python s4_take.py CHOLAFIN --skip "sector Stage 4"            # passed on it — say why

This is the step that turns the Log from a diary into a score, and it is the step that gives the journal a real entry instead of a backfilled one. It:

  1. finds the latest review of the name (and TF, if given);
  2. reads the plan the reviewer settled on — R-CHECK's entry and stop and the canon T1/T2, never the model's own targets — plus the trade type and the ruling;
  3. appends a ## TAKEN (or ## SKIPPED) block to the review file — the file is the record;
  4. fills my_call and agreed on that row of the CSV (agreed = did your call match the ruling);
  5. TAKEN: writes the journal OPEN row through dhan_journal_v7.upsert_trade with the stop, both targets, Timeframe (Positional / Swing — rung 1 of the trade-type ladder), setup, planned R:R, and the review as the rationale. The upsert hook captures the true entry snapshot, so the 16:30 journal sync tomorrow only has to confirm qty and average from Dhan;
  6. rebuilds the Reviewer Log so the row shows your call.

--sl overrides the stop, --note adds free text to the block and the rationale, --no-journal marks the review only. A SKIPPED with a reason is not a lesser entry — it is the control group.

13What it is not

  • Not a signal. It never surfaces a name. GO rows, Buy Trigger Live rows, alerts, your command — nothing else reaches it.
  • Not the plan of record. S4 is. The reviewer's plan is what it would change and why; the R-CHECK canon is the arithmetic.
  • One plan per trigger, since 20 Sep. S4 now latches the stop to the trigger bar as well as the entry, so the R-CHECK line, s4_take and the journal read the same SL/T1/T2 however many bars after the trigger the review ran. Before that a tested zone could move the stop between the alert and the read.
  • Not validated. No review has an outcome attached yet. The my_call / agreed columns and the TAKEN blocks are how it earns or loses trust — after twenty-odd scored rows the Log can say whether its rulings beat the template, and whether your overrides beat its rulings. Until then it is a well-read colleague, not an authority.
  • Not reading Geometry, Levels or the Read on S5 — withheld until the classifier is field-verified (Doc 30).
  • Not intraday-fast. Ninety seconds after a bar close is the design; the alert marks a bar and the bar does not change. Do not size the queue for speed.
