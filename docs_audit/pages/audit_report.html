The Library Audit

Twenty-four guide pages, checked against the code rather than against the notes. Most were sound. The ones that were not had drifted in a particular way — not wrong numbers so much as missing states: a lifecycle one stage short, a navigation map missing its first group, a matrix missing its fifth column.

Method

§What the audit actually did

Every claim was checked at its source file and line. Where a page and this project's own notes disagreed, the code decided — and twice the notes lost, so they were corrected too.

Three tools carry the work forward. code_truth.py reads 47 values straight out of the modules; truth_watch.py reports which of them moved and names the pages citing each one; rank_pages.py scores every page for contradictions and for gaps it specifically owes. All 24 pages now score zero.

Why a checker, and not just a careful read

A guide does not announce that it has gone stale. It reads exactly as well on the day its number stops being true as it did the day before — which is what makes documentation drift the same shape as the silent failures already catalogued on the operating-loop page. So it was added there as the ninth one, with a post-close job to match.

The checker earns its place by being wrong in a useful direction: it flags, it does not edit. Five of its early hits were pages correctly describing their own history — a superseded number quoted as superseded. Those were fixed in the checker, never in the prose.

The findings that matter

§Two numbers, two modules, one question

The single-page corrections are listed further down. These two are different in kind: nothing on either page was wrong. The disagreement is between modules, which is exactly the class of defect a page-by-page read cannot find and a reader meets only at the moment it costs them something.

What a recovery trade targets

The screener plans2.5R The T1 on the signal row — the number you read when deciding whether the setup has room.
The exit policy places3R, then 5R Taking a quarter at each. The legs that actually rest at the broker.

At the order, the exit policy wins. The screener's figure is a reward-plausibility check at screening time, and Doc 09 now says so — but two modules answering one question with two numbers is a gap, not a design.

What "beaten down" is measured against

The signal test wants15–35% off a rolling 60-bar high.
The regime test wants10–40% off the 52-week high.

A name 20% below its two-month high can sit 45% below its yearly one — passing the first test and failing the second, with neither number meaning what the other reports.

Both were left unfixed in code, on purpose

Each sits inside signal output. Changing either moves what the pending recovery re-baseline is measuring, and a correctness fix applied during a measurement produces a result that answers neither question. Both are now watched as pairs, so if one side moves and the other does not, the watcher names both pages.

Recommendation

§What to do about the gaps

In priority order. The first two are decisions, not edits — and both want the pending recovery re-baseline in hand before they are made.

  1. 01 Settle the recovery target Either the screener plans 3R to match the policy, or the screener's number is renamed to what it actually is — a screening-time R:R check, not a target. Read the re-baseline first: the current 2.5 is what that run is measuring. decision
  2. 02 Pick one reference high for "beaten down" The 60-bar and 52-week tests are asking the same question of the same stock. One of them should move; which one is a trading judgement about whether recovery is a two-month or a one-year idea. decision
  3. 03 Make the sector map one command Both generators read the same database, so the only real risk is running one and not the other. Wrap them together, and have the wrapper print the reminder that the library still needs publishing — the step that gets forgotten, because the local edit compiles cleanly while every importing script stays pinned to the old version. small fix
  4. 04 Retire the rungs that cannot be reached Structure Health's BROKEN tier and the choppy-range setup share one threshold that has never been met. A live tooltip still offers "BROKEN (4+)" as though it were a state you might see. Either lower the threshold to something reachable or say plainly that the scale is two-valued — but do not leave a dead condition reading as a working safeguard. small fix
  5. 05 Write the two missing fixtures An extension event and a window-boundary case, so all seven strict-trend fixes have a test that fails without them. Until then, those two behaviours are held in place by nothing but the code being currently correct. small fix
  6. 06 Let the post-close check run, and read what it flags It reports which facts moved and which pages cite them. A moved fact is not automatically a stale doc — sometimes the code change was the mistake. That is the point of reporting rather than auto-correcting. standing
The one thing this audit cannot do for you

Every page now agrees with the code. That is a statement about consistency, not about edge. A guide that accurately describes a parameter says nothing about whether the parameter earns its place — and several of these pages exist precisely to record that a tested idea was rejected. Keeping those honest is what the library is for.
